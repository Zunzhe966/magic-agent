## 〇、本次改版说明（读旧文档前先看到这里）

产品定位从「魔法代理」升级为**「网络管理」**：它不是又一个代理客户端，而是本机网络的**管理员**——无论网络状态混乱到什么地步（多个代理软件并存、残留路由、半开的系统代理、端口被占），只要它开启，就要能把一切**归为秩序**。

旧文档中以下思想**已废弃**，凡与之冲突的表述以本文为准：

| 旧思想 | 为什么错 / 危险 | 现在的立场 |
|---|---|---|
| "启动时自动清理第三方代理，保证本程序是系统唯一代理" | 只杀进程不接管配置，且未经用户确认就动别人的东西；清理完也不检查路由/DNS/端口残留——这不是管理员，这是抢地盘 | 接管要**先审计、再征得同意、逐个收编、记账、可回滚**（见 §五 一键归序） |
| `allow-lan: false` 能管住 listeners | **实测证伪**（2026-09-23）：mihomo 的 `listeners` 段不受 `allow-lan` 约束，不写 `listen:` 时默认绑 `0.0.0.0`，局域网可匿名白嫖节点出口 | 每条 listener 必须显式 `listen: 127.0.0.1`，有单测回归锁死 |
| `bind-address` 可以限制 listener | 实测无效（同版本仍绑 0.0.0.0），只有 `listen:` 生效 | 统一用 `listen:`，文档不再提 bind-address |
| root 写的日志可以是默认权限 | root umask 020 → 日志 0644 世界可读，里面是全机连接记录（进程→域名），同机任何账号可读取用户隐私 | 两条启动路径都强制 `umask 077` + 对存量日志 `chmod 600` |
| 系统代理"任一服务设置成功即报成功" | 多网络服务场景下 UI 显示假状态，用户无法信任面板 | **逐服务对账** ✅ 已修复（2026-09-23，v0.2.11）：如实报告每个服务的成败 |
| "状态查询报真实状态"已经做完 | `status()` 读 `scutil --proxy` 是真实值没错，但它给的是**全局视图**，与 networksetup 的**逐服务写入**口径不一致 | 真实状态 = 逐服务读回比对，不止看 scutil 汇总 |

另澄清一条能力边界：**本项目没有 SSH 端口转发/隧道功能**（全源码、UI、MCP 均无 `-L`/tunnel，历史上也从未实现过；2026-09-23 排查中曾出现误报，特此固化说明）。SSH 能力只有交互终端与非交互执行两种。

## 一、这个软件是什么

一句话：**本机网络的管理员——把混乱的网络状态一键归为秩序，并让每个软件、每条流量各走各路。**

它管四件事：

1. **出口秩序**：谁走节点代理、谁走本机直连，精确到每个软件、每个域名，且物理上分路隔离（7893/7892），进去后不再被二次判断。
2. **系统级接管**：系统代理、路由、DNS、端口占用——开启时审计并接管一切混乱来源，关闭/崩溃时可还原。
3. **云服务器控制**：内置 SSH 终端 + 探针 + 快捷命令，代理服务器和登录管理共享同一套凭据体系。
4. **AI 可操控**：通过 MCP（30 个工具）暴露给 AI 客户端，智能体拿实测数据自主选路，而不是靠规则猜。

### 管理员 vs 代理客户端的分界

普通代理客户端回答"怎么连上节点"；网络管理员必须回答这三个问题：

- **现在本机网络到底是什么状态？**（完整审计：进程、端口、路由、DNS、系统代理逐服务、PAC、环境变量）
- **混乱是谁造成的？**（竞品内核、残留路由、半开代理配置——逐个指认）
- **一键之后会发生什么、怎么撤销？**（接管清单 + 账本 + 回滚）

现状诚实评估：第 1、2 问已有雏形（`find_foreign_proxies`、`check_conflicts`、`doctor`），但**不完整**（不查路由/DNS/PAC/env，不逐个征询）；第 3 问**完全没有**（无账本、无回滚）。这是重构的主线，详见 `docs/重构计划.md`。

## 二、要解决的问题

用户机器上的真实混乱（本产品诞生的原因）：

- FlClash/Clash Verge/sing-box 等多个代理软件曾装过、崩过、留过残骸：改过的系统代理、没清掉的路由、占着的端口。
- TUN 全接管 + `MATCH,GLOBAL` 把整台电脑塞进隧道，国内国外混在一起，例外只能手工猜域名。
- 某个代理崩了，系统代理还指向已关闭的端口 → 全机莫名断网，没人知道为什么。
- AI 智能体上网时不知道哪条路通，凭规则猜，猜错了请求超时或污染。

**核心需求（不变的部分）**：按软件分流——电脑上所有联网软件是一张清单，每个独立指定走代理/直连。
**核心需求（升级的部分）**：开启即归序——不管接手时多乱，点一下"启动"之后，系统网络状态收敛到一个确定的、可解释的、可还原的秩序态。

## 三、和现有代理软件的对比

| 维度 | Clash Verge / FlClash / Surge | 网络管理（本产品） |
|---|---|---|
| 角色 | 代理客户端（自己上网） | **网络管理员**（接管整机网络状态） |
| 分流粒度 | 域名/IP 规则为主，全局 TUN 接管 | **按软件（进程）精确分流**，每 App 独立设置 |
| 国内外判断 | 软件自动判断，用户不可见 | **双路显式出口** 7892/7893，决策权交给用户/AI |
| 对第三方代理 | 共存或互相抢端口 | **审计→确认→接管→记账→可回滚**（规划中；现状为启动强清，属过渡实现） |
| 崩溃善后 | 各自随缘 | 看门狗自愈 + 退出钩子 + （规划）账本回滚 |
| 服务器管理 | 无 | 内置 SSH 终端 + 探针 + 快捷命令 |
| AI 集成 | 无 | 28 个 MCP 工具，实测路况自主决策 |
| 资源占用 | Electron 80~200MB / 120~400MB | Tauri 2~10MB / 30~50MB |
| 隐私/安全 | 参差不齐 | DNS 全加密 + 配置/日志 0600 + API 带 secret + listener 钉死回环 + Keychain |

### 差异化优势（按重要程度）

1. **一键归序是产品承诺**：开启动作的语义不是"把我的代理打开"，而是"把这台机器的网络交给我管"。
2. **按软件分流第一等公民**：扫描出 App 清单勾选即可，不是藏在规则编辑器里的 `PROCESS-NAME`。
3. **双路物理隔离 + 实测决策**：mihomo 不做二次判断，AI/人用 `probe_route` 实测后拍板。
4. **上网 + 管服务器合一**：代理节点与 SSH 主机同源同凭据，一次配置。
5. **轻量常驻**：Tauri 架构适合 24h 后台。
6. **协议最严格档**：VLESS + Reality + XTLS Vision，抗主动探测。

### 如实的不足（2026-09-23 盘点）

1. **"归序"目前只是半成品**：有清理第三方、有看门狗、有退出钩子，但没有全局审计（路由/DNS/PAC/env）、没有接管账本、没有回滚。距离"开启即归序"的产品承诺还有整个 P1 阶段的距离。
2. ~~**系统代理写入会报假账**~~ ✅ 已修复（2026-09-23，v0.2.11）：`any_success` 已替换为逐服务读回对账，部分失败如实点名。
3. **仅 macOS**。
4. **按软件分流有边界**：系统代理只对遵守它的软件生效；TUN strict-route 补了一部分，但 Telegram/部分游戏/命令行工具仍可能绕开，界面标"未接管"，不宣称全管。
5. **协议以 VLESS + Reality 为主**，SS/Trojan/Hysteria2 未全覆盖。
6. **ad-hoc 签名**：未做 Developer ID 签名与公证，Gatekeeper 拒绝，拷贝部署体验差（发版铁律依赖用户右键放行，属于债）。
7. **单机定位**：无多设备同步。

## 四、技术选型（结论不变，理由保留一句）

- **桌面壳 Tauri 2**（Rust + Vue3）：体积/内存适合 24h 常驻，Electron 是硬伤。
- **代理内核 mihomo**（外部独立二进制，一行代码不进工程）：只做"转发到节点"，用成熟实现。⚠️ 注意：内核成熟 ≠ 我们喂给它的配置正确——listener 绑 0.0.0.0 的事故恰恰是我们生成的配置缺字段。**用别人的内核不是问题的原因，对别人配置的语义理解错误才是。**
- **协议 VLESS + Reality + XTLS Vision**：现行隐蔽性最高组合。
- **SSH 系统 `ssh` + `expect`**（非 russh）：零重依赖取舍，凭据经 stdin 不落 argv。
- **凭据 macOS Keychain**（`/usr/bin/security`）。
- **MCP Python 纯标准库**。

### 「从零写」的边界（不变）

产品代码 100% 自写；Tauri/mihomo/xterm.js/VLESS 协议属基础设施。真正自研的差异化价值：按软件分流引擎、mihomo 生命周期与配置生成、系统代理读写、双路探测、（规划中）归序引擎与账本。

## 五、核心设计：一键归序（目标架构）

这是"网络管理员"定位的功能闭环，五步。现状与目标逐条标注：

### 第 1 步 · 审计（Audit）

开启前对整机网络状态做一次全量快照：

- 代理类进程（已有：`find_foreign_proxies`，24 组 App + 12 内核名，只匹配可执行路径防误杀）
- 关键端口占用（已有雏形：`check_conflicts` 只查 7891；目标：7891/7892/7893/19091/1054 + 常见代理端口 1080/7890/8118/10808/10809）
- **路由表残留**（无 → 新增：`route -n get default` + utun 接口清点，识别历史 TUN 事故留下的黑洞路由）
- **DNS 配置**（无 → 新增：`scutil --dns` 首尾比对，识别被改走的 resolver）
- **系统代理逐服务现状**（部分：`scutil --proxy` 全局视图；目标：`networksetup -getwebproxy <svc>` 逐服务）
- **PAC / 自动配置**（无 → 新增：`ProxyAutoConfigEnable` 检测）
- **shell 环境变量 http_proxy/ALL_PROXY**（无 → 新增：只报告不修改，提示用户哪些终端会话会受影响）

### 第 2 步 · 接管（Take over）

- 对审计发现的每个混乱源，给出**处置方案**（停止/等待/保留），首次需用户逐项确认；确认后记住策略（"以后这类直接办"）。
- 现状是"启动 800ms 后无条件 SIGTERM→SIGKILL 全部第三方"——保留该行为作为**快速模式**，但默认走确认流程。
- 绝不碰的白名单：自身 runtime 内核、用户标记"共存"的软件。

### 第 3 步 · 账本（Ledger）

接管前的每一处改动登记原值，存 `ledger.json`（原子写 0600）：

```
{ ts, items: [ {kind: system_proxy|process|route|dns, service/pid/key, before, after, reversible} ] }
```

- 不可逆项（如杀掉的第三方会话数据）明确标 `reversible: false`，UI 上灰显。
- 账本是"一键还原"的数据基础，也是排查"到底是谁改了网络"的证据链。

### 第 4 步 · 归序（Order）

把所有出口收敛到确定状态：

- 内核配置三条监听全部钉死 `127.0.0.1`（7891 mixed / 7892 direct-only / 7893 proxy-only）✅ 已完成（2026-09-23 修复）
- 系统代理逐服务设置为 7891 并**读回验证** ✅ 已完成（2026-09-23，v0.2.11）
- 保命直连名单（PROTECTED_DIRECT_DOMAINS）优先级最高 ✅
- 归序完成的定义 = **回读全部一致**，而非"命令都发出去了"。

### 第 5 步 · 巡检与回滚（Watch & Rollback)

- 看门狗（已有：30s 探活 + ctl 重启 + 失败关系统代理）扩展为**漂移检测**：定期回读账本各项现值，发现被外部改动 → 提示"重新归位"或"接受新状态并更新账本"。
- 一键还原：按账本逆序恢复，含停自己的内核。
- 崩溃兜底：孤儿内核场景已有 pgrep 重新发现 + 提权 kill 兜底；目标是启动时若发现自己有上次未结的账本，先完成回滚再进入新会话。

## 六、关键技术边界（不夸大）

1. 进程分流不是 100%：系统代理只管遵守者；TUN strict-route 只拉"明确要代理"的流量，其余走原生直连。
2. `tun.auto-route` 永远 false（禁区：改 true 会接管默认路由，重演 2026-09-03 劫持事故）。
3. mihomo PATCH `/configs` 对多条 PROCESS-PATH-REGEX 只保留第一条 → 热重载必须写全量 YAML + SIGHUP。
4. macOS `listeners` 绑定只认 `listen:` 字段（bind-address 无效、allow-lan 不覆盖）——改内核版本后要重跑 §七 验收实验。
5. SSH 私钥/密码只进 Keychain，配置 JSON 不留明文；expect 脚本密码走 stdin。
6. 「自动」策略用真实 DNS 解析，不开 fake-ip。

## 七、验收实验（安全红线的事实依据）

2026-09-23 实测方法（改内核版本后必须重跑）：

```yaml
listeners:
  - {name: t1, type: mixed, port: X, bind-address: 127.0.0.1}   # → 仍 *.X（字段无效）
  - {name: t2, type: mixed, port: Y, listen: 127.0.0.1}          # → 127.0.0.1.Y（生效）
  - {name: t3, type: mixed, port: Z}                              # → *.Z（默认通配）
```

判据：`netstat -an -p tcp | grep LISTEN` 对应行必须是 `127.0.0.1.`。
固化位置：Rust 单测 `generated_conf_is_valid_mihomo_yaml` 断言含 `listen: 127.0.0.1`；`check_parity.py` 保证 MCP 侧同步。

## 八、适合谁 / 不适合谁

**适合**：受够多代理软件互踩、需要"一个开关管住全部网络出口"的人；既要精细分流又要顺手管云服务器的人；希望 AI 助手拿实测数据自主选路的人。

**暂不适合**：需要 Windows/Linux/移动端的人；依赖海量规则订阅的重度 Clash 用户；要求开箱即用零授权弹窗的人（TUN/root 是硬约束）。
