# 魔法代理：需求与设计

## 1. 我们在做什么

做一个 macOS 桌面软件，名字叫“魔法代理”。它做两件事：

1. **网络代理**：通过用户自己的云服务器节点上网。
2. **云服务器控制**：在软件里直接连接、查看、操作那台云服务器。

它不是又一个 FlClash，它要把“按软件分流”和“服务器管理”做成同一个产品的核心体验。

## 2. 用户现在遇到的问题

用户本机用 FlClash，感觉“混乱、不智能、全局、一点不好用”：

- 当前是 TUN 全接管 + `MATCH,GLOBAL`，整个电脑几乎所有流量都进代理。
- 例外只能手工猜域名（zhihu、jd、银行域名），不是按软件控制。
- Chrome、Safari、QQ、微信、Codex 等全部混在同一个代理里，无法精确说“Chrome 走云服务器、Safari 走本机”。

## 3. 核心需求：按软件分流

产品最重要的能力，是把“这台电脑上所有联网软件”做成一张清单，每个软件都可以精确指定：

- **走代理**：这个软件的流量全部走云服务器。
- **直连**：这个软件的流量全部走本机网络。
- **自动**：按照内置规则自动判断（默认国内直连、境外走代理）。

界面要能扫描当前运行的 App，显示 Chrome、Safari、微信、QQ、Telegram、Doubao 等，还能列出常驻后台进程，让用户看得见、改得动。

技术路线：mihomo 作为本地代理引擎，关闭 TUN 全接管，改用“系统代理 + 进程规则”，这是 macOS 上最稳的按软件分流方式。已知边界会在第 6 节写清楚，不夸大能力。

## 4. 核心需求：云服务器控制

用户自己有一台云服务器，上面的节点是 VLESS + Reality（当前 FlClash 配置里能看到：104.160.40.35，两个节点）。

“控制云服务器”至少包含：

- 添加/保存多台服务器连接（主机、端口、用户名、密钥/密码、备注）。
- 内置 SSH 终端：像 FinalShell 一样直接在软件里敲命令。
- 快捷命令：常用操作一键执行，例如查看系统信息、看代理服务状态、重启代理服务、看内存/磁盘。
- 连接状态显示：在线/离线、系统信息、CPU/内存/磁盘占用。

这样用户不再需要为“上网”开一个软件、为“管服务器”再开一个软件。

## 5. 系统架构

```
┌──────────────────────────────────────────────┐
│  魔法代理 桌面端 (Electron)                    │
│  ├─ 概览：代理状态、流量、节点、服务器状态      │
│  ├─ 应用分流：扫描 App + 每个软件代理/直连/自动 │
│  ├─ 云服务器：SSH 终端、快捷命令、连接管理      │
│  └─ 日志：代理连接日志、错误日志               │
└──────────────┬───────────────────────────────┘
               │ IPC
┌──────────────▼───────────────────────────────┐
│ 主进程                                        │
│  ├─ ProxyEngine：启动/停止 mihomo，生成配置    │
│  ├─ AppProfiler：扫描进程、维护软件策略       │
│  ├─ ServerManager：ssh2 连接、终端、命令      │
│  └─ Store：本地 JSON 持久化                    │
└──────────────┬───────────────────────────────┘
               │
        ┌──────▼──────┐    ┌──────────────────┐
        │ mihomo 内核 │    │ 云服务器 (SSH)    │
        │ 本地代理端口 │    │ 节点/VLESS/Reality│
        └─────────────┘    └──────────────────┘
```

- 代理节点配置复用用户现有 VLESS + Reality 参数。
- 系统代理由软件设置到 macOS（HTTP/SOCKS 端口），不强制 TUN。
- 配置、节点、服务器连接、软件策略全部存本地 JSON，不上传。

## 6. 技术边界（诚实说明）

macOS 上“强制某个软件完全走代理或完全绕开代理”做不到 100%，原因：

- 系统代理只对遵守系统代理的软件生效（浏览器、大部分 App 会遵守）。
- 不走系统代理的软件（Telegram 默认直连、某些游戏/命令行）需要额外手段。
- 完整方案是 TUN/Proxifier 那种强制接管，但这会重新引入“全量混乱”和稳定性问题。

本产品优先做到可靠、可理解：系统代理 + 进程规则 + 清晰的“已识别/未识别”状态。这是用户场景里最实用的平衡点。

## 7. 范围与优先级

第一版先做：

- 代理：节点管理（VLESS/Reality）、启动/停止、模式切换、应用分流清单。
- 服务器：SSH 连接、终端、快捷命令、状态显示。
- 本地存储与日志。

暂不做（除非后续要求）：复杂规则编辑器、机场订阅自动更新、多设备同步、Windows/Linux 版本。

## 8. 验收标准

1. 能添加用户现有 VLESS+Reality 节点并成功启动代理。
2. Chrome 配置为“走代理”后，其访问境外站点经过云服务器；Safari 配置为“直连”后，其访问走本机。
3. 软件能扫描出本机主要联网 App 并在界面中分类。
4. 能在软件里 SSH 连接到云服务器，执行命令并看到输出。
5. 所有数据本地保存，重启软件不丢失。

## 9. 设计自查：冲突与坑（必须解决）

1. 规则优先级必须明确：**先按软件，再按全局自动**。某个软件被设为“直连”时，不能被后续“境外走代理”规则覆盖；被设为“代理”时，也不能被“国内直连”覆盖。
2. Safari 的实际联网进程不是 Safari 主进程，而是 `com.apple.WebKit.Networking`；Chrome 是 `Google Chrome` + 一堆 `Google Chrome Helper`。因此“按软件”必须按 App 包路径匹配整组进程，不能只匹配主进程名。
3. 系统代理模式只能控制“遵守系统代理”的软件。Telegram、部分游戏、命令行程序可能自己直连，产品要把这些标成“未接管”，不能宣称全管。
4. 如果 FlClash 还在运行，会抢系统代理/端口。魔法代理启动前要检测 FlClash/mihomo/7890，提示用户关闭，避免冲突。
5. SSH 密码和私钥不能明文写进 JSON。使用 macOS Keychain（Electron safeStorage）加密后落盘。
6. “自动”策略用国内直连/境外代理时，DNS 必须走系统真实解析，不启用 fake-ip，避免本地软件域名解析错乱。
7. mihomo 的 PROCESS-NAME 在 macOS 上存在已知不稳定问题。本项目不依赖 TUN，改用系统代理 + PROCESS-PATH-REGEX，并在本机用 Chrome/Safari 对照实测验收。
8. 应用扫描要区分“正在运行的软件”和“后台系统服务”，后台 helper 归入所属 App，不单独占清单。

## 10. 可行性

- mihomo v1.19.30（darwin arm64）已下载并验证可运行。
- Electron 34 + Forge 项目骨架、依赖已就位。
- SSH 采用纯 JS 的 ssh2 库，不依赖原生编译，xterm.js 做终端。
- 主要风险只剩 macOS 进程匹配的实际表现，可通过本机 Chrome/Safari 对照测试验证。
- 结论：按当前设计可以做成，不需要发明新技术，都是成熟组件组合。

## 11. 工期估计

- 核心可运行版（代理 + 应用分流 + SSH 终端 + 界面）：连续开发约 1-2 小时工作量，今天可跑通。
- 正式 .app 打包、图标、签名、异常恢复、长时间稳定性：再半天到一天打磨。


## 12. 技术选型（用户确认）

- 桌面壳：Tauri 2（Rust 后端 + Web 前端），不用 Electron。
- 后端语言：Rust，负责 mihomo 进程管理、系统代理、SSH、配置存储。
- 前端：HTML/CSS/JS，通过 Tauri IPC 调用 Rust。
- 代理内核：mihomo（Go 编写，作为外部进程调用，不重新实现协议）。
- SSH：Rust 侧使用 ssh2/thrussh 类库或调用系统 ssh，终端由 Web 端 xterm.js 渲染。
